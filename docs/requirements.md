# Atoms-Demo 需求规格

本版新增[第 19 节 · 长期演进与个人代表作规格](#19-长期演进与个人代表作规格)（`GOAL-006`～`GOAL-009`、`FR-025`～`FR-032`、`NFR-011`～`NFR-015`、`AT-021`～`AT-028`），作为项目长期公网展示与工程化演进的增量契约。

历史增量：[第 17 节 · 创作入口与体验更新](#17-创作入口与体验更新)（FR-016～FR-020、AT-012～AT-017，见[技术规划 v1.2](./technical-plan.md#27-创作体验更新实现计划)）；[第 18 节 · 生成规划与交付验收增量](#18-生成规划与交付验收增量)（FR-021～FR-024、AT-018～AT-020，见[技术规划第 28 节](./technical-plan.md#28-规划专业实现与效果审核)）。第 1～16 节继续定义首版主流程、匿名积分和笔试交付要求。

## 1. 文档用途与约束

本规格描述一个通过自然语言生成、预览和持续修改 Web 应用的产品原型。后续 AI 应据此开展技术规划：明确支持边界、比较方案、划分模块、设计数据与任务流程，并制定实现和验收计划。

本规格包含三类信息，必须保持区分：

| 标记 | 含义 | 如何使用 |
| --- | --- | --- |
| EXAM | 原题明确提出的要求或建议 | 按表中“强制/建议”分别处理，不得篡改原题约束 |
| BASELINE | 根据题意及产品调研提出的首版需求 | 是本次技术规划的默认范围；仍属于可讨论的需求草案 |
| REFERENCE | Atoms 已有能力 | 用于理解产品和选择扩展，不自动变成首版必做项 |

优先级定义：P0 为默认首版闭环；P1 为可选择的延展能力；P2 为本次默认排除的完整平台能力。P0/P1 是本规格的范围建议，并非原题逐项规定，也尚未经过用户逐项确认。

技术规划可以基于下述默认值继续推进。遇到未知条件时，列明假设、替代方案及影响；只有影响真实实施的必要条件才需要在实施前解决。此阶段不预先指定框架、语言、数据库、模型厂商、单文件或多文件代码形式、预览运行环境及部署平台。

## 4. 产品目标、角色和术语

### 4.1 产品目标

- GOAL-001：用户描述一个明确的 Web 应用需求后，可以得到并操作生成结果。
- GOAL-002：用户可以继续提出修改，在已有结果上迭代，观察此次修改的结果。
- GOAL-003：项目、请求和有效代码可以保存、重新打开及恢复预览。
- GOAL-004：用户可以知道当前正在处理什么、是否完成，以及失败后如何继续。
- GOAL-005：评审能够在线走通代表流程，并从源代码和说明文档理解实现边界与取舍。

### 4.2 使用角色

| 角色 | 目标 |
| --- | --- |
| 应用创建者 | 描述需求、检查结果、提出修改、重新打开项目 |
| 评审访客 | 使用在线 Demo 验证真实功能，查看提交说明和代码 |
| 生成应用的最终用户 | 在预览或独立页面中使用生成应用的按钮、输入、筛选等功能 |

BASELINE 默认提供无需注册的评审体验。多人团队、账户管理及组织权限见 P2；访客数据隔离仍须满足 NFR-004。

### 4.3 核心术语

| 术语 | 定义 |
| --- | --- |
| 平台 | 本次开发的 Atoms-Demo |
| 生成应用 | 平台根据用户需求生成的可交互 Web 成果 |
| 项目 | 承载需求、消息、运行记录、代码和版本的工作单元 |
| 运行 Run | 一次生成、修改或修复请求的执行实例 |
| 阶段事件 | 对实际执行动作和结果的记录，如开始生成、产物校验、预览就绪 |
| 代码产物 | 可查看、保存并被预览环境加载的代码及必要资源；形式由技术规划决定 |
| 版本 Version | 一次成功交付的不可变代码产物快照 |
| 当前版本 | 项目当前工作所基于的版本 |
| 最后可用版本 | 最近一次通过本项目规定的基础校验、可恢复预览的版本 |
| 预览 | 平台内可运行并操作生成应用的环境 |
| 发布版本 | 已提供独立外部访问的生成应用版本；仅在选做发布功能时存在 |

## 5. 建议首版范围

### 5.1 P0 默认闭环

创建/打开项目 → 输入需求 → 真实 AI 生成 → 查看执行状态和代码 → 操作预览 → 继续修改 → 保存版本 → 刷新或重新打开后继续。

P0 覆盖：项目入口、自然语言请求、生成与修改、执行反馈、代码查看、可交互预览、平台数据持久化、失败恢复、在线交付。

代表产物至少覆盖有状态交互的前端 Web 应用，例如任务看板或计算器。是否支持多文件工程、第三方依赖、后端代码和任意命令执行，属于技术规划必须明确的产物边界。界面和说明不得宣称超出实际支持范围的生成能力。

### 5.2 P1 可选延展

技术规划应按依赖、投入和演示价值评估 P1。建议优先比较“版本恢复”和“源码导出”；实际选做集合须在技术计划中明确，不能默认全部实现。

### 5.3 P2 默认排除

- 完整 Atoms Cloud 管理控制台、数据库运维台、身份验证服务或密钥库产品。
- 多工作区、团队邀请、细粒度成员权限、完整账户系统。
- GitHub OAuth 连接器及双向同步；提交本项目源码到 GitHub 仍是 EXAM-005。
- 任意第三方服务连接器、Stripe 支付、事务邮件平台、定时任务平台。
- GA4、SEO 内容运营、Google Ads 投放及其管理控制台。
- 原生移动应用、MP4 视频、PPTX 幻灯片和文档文件生成工作流。网页幻灯片和网页分镜属于第 17 节定义的浏览器交付物。
- 通用深度研究、完整多模型赛马及全量模型管理。
- 套餐、订阅、支付、域名购买及自动 DNS 管理。匿名用户积分余额与按 token 扣费已由用户明确选入 P0，见 FR-013～FR-015。

以上排除的是完整产品功能。技术实现可以使用数据库、身份验证组件、模型接口或托管服务来支撑 P0；使用基础设施不等于需要构建其管理平台。

## 6. P0 功能需求及验收标准

### FR-001 评审入口与支持范围

- 来源：BASELINE；关联 EXAM-004、EXAM-009。
- 用户打开在线 Demo 后，无需创建账户即可进入可操作的创建入口。
- 首次使用时可看懂平台能生成什么，并可使用一个示例需求。
- 未配置模型或服务不可用时，明确显示配置/服务状态。示例结果若存在，必须标为示例，不能冒充本次 AI 生成。
- AC-001：在新的访客上下文中打开提交 URL，能够找到需求输入及生成入口；不存在必须注册才能评审的步骤。

### FR-002 项目创建、列表与重新打开

- 来源：BASELINE、SRC-START。
- 创建项目后生成稳定项目标识和名称；名称可由初始需求生成，也可使用明确的默认名称。
- 项目列表显示名称、最近更新时间和可理解的状态；可以重新打开已有项目。
- 重命名、删除、搜索和文件夹组织不是本项的必做条件。
- AC-002：创建两个不同项目后，能够分别重新打开；代码、消息和当前版本不混入另一个项目。

### FR-003 初始需求提交

- 来源：BASELINE；关联 EXAM-001。
- 接收非空的自然语言需求，建立用户消息并创建一次 Run。
- 对空白输入、超过配置上限的输入给出清晰反馈，不启动实际生成。
- 同一项目存在活动 Run 时，P0 默认阻止重复执行并说明原因。用户请求队列属于 FR-101。
- AC-003：有效请求产生唯一可识别的 Run；双击提交或网络重试不得无意产生两个等价任务。

### FR-004 真实代码生成与基础校验

- 来源：BASELINE；关联 EXAM-001、EXAM-002；参考 SRC-AGENT。
- 使用真实模型处理需求，生成符合支持范围的代码产物，并触发相应基础校验与预览准备。
- 每次 Run 关联实际使用的需求、项目和基础版本。校验方法及通过条件必须在技术计划中明确。
- “已生成代码”“基础校验通过”“预览可用”是不同事实。模型宣称完成，不能单独作为预览成功依据。
- 智能体数量、内部编排和工具机制由技术规划决定。界面只能展示实际发生的动作、参与者和结果。
- AC-004：使用两个不同的有效需求时，实际调用生成能力，得到与各自需求相关的代码和预览；固定模板回填不能代替实际生成。

### FR-005 执行状态和阶段反馈

- 来源：BASELINE、SRC-AGENT。
- Run 至少区分 pending、running、succeeded、failed、interrupted；可显示简洁中文名称。
- 活动期间提供可理解的阶段反馈；错误和终态明确可见，禁止无期限显示“生成中”。
- 阶段摘要、时间和可观测操作可以展示；不得编造工具记录、成功检查或虚构角色交接。
- AC-005：成功、失败和中断场景均有明确状态；成功只在 FR-004 的交付条件满足后出现。

### FR-006 代码查看

- 来源：BASELINE、SRC-EDIT。
- 可以查看当前预览对应的代码和版本标识。
- 若产物包含多个文件，可以定位并查看相应文件；若为单文件产物，应明确其形式。
- 代码查看不能显示模型密钥或平台服务端凭据。手动编辑属于 FR-104。
- AC-006：在预览与代码之间切换后，二者对应同一版本；切换项目或版本后不残留错误的代码内容。

### FR-007 真实交互预览

- 来源：BASELINE；关联 EXAM-001、EXAM-002；参考 SRC-PREVIEW。
- 可以运行生成应用，操作其主要按钮、输入、列表或计算等行为。
- 预览至少区分 starting、ready、failed，并标明对应项目与版本。
- 支持重新加载预览。设备尺寸切换和新窗口打开可在 P1 中评估。
- 新版本准备期间应保留最后可用结果，或明确显示尚无可用结果。
- AC-007：生成任务看板后，能添加任务、切换完成状态并筛选；这些操作改变实际应用状态。截图和静态 HTML 展示不能通过本项。

### FR-008 在现有结果上迭代

- 来源：BASELINE、SRC-AGENT、SRC-START。
- 用户可以在同一项目内提出后续修改，运行应基于当前明确版本及相关上下文。
- 修改完成后创建新版本，并显示变更摘要。不得将修改请求无提示地作为新项目从零处理。
- 未被请求修改的重要能力应被保留；代表流程必须进行验证，不能仅依赖模型承诺。
- AC-008：在任务看板上要求“增加优先级筛选，保留添加任务和完成状态功能”，新结果具备新能力，原有两项交互仍可使用。

### FR-009 版本记录与当前版本一致性

- 来源：BASELINE、SRC-HISTORY。
- 每次成功交付创建独立版本，记录项目、基础版本、来源 Run、时间和摘要。
- 已完成版本的代码快照不可被后续生成覆盖；项目当前版本引用可变化。
- 用户可识别当前版本和最后可用版本。历史恢复和克隆见 FR-105、FR-106。
- AC-009：初次生成及一次修改后，可区分两个版本；第二次修改失败时，已有成功版本及其代码仍然保留。

### FR-010 平台数据持久化

- 来源：BASELINE；关联 EXAM-003。
- 保存项目、用户请求、结果摘要、Run 终态、版本元数据及代码产物；保留恢复预览所需的资源引用。
- 持久化方式不限，但必须明确保留范围：同一浏览器、跨标签页、跨设备以及服务重启后的行为。
- 默认验收至少覆盖同一访客上下文中刷新页面、关闭标签页并重新打开后的恢复；不能只依靠页面内存。
- 平台重启、重新部署、数据清理的边界应在技术计划和交付说明中写明。
- AC-010：成功生成并修改后刷新/重新打开平台，项目、两次请求、当前代码和版本记录仍可读取，并能重新进入可操作预览。

### FR-011 失败、重试及恢复

- 来源：BASELINE、SRC-PREVIEW。
- 区分模型请求失败、代码/构建校验失败、预览准备失败和连接中断；提供用户可理解的反馈及下一步。
- 失败不覆盖最后可用代码。手动重试产生新的可追踪 Run，并保留原失败记录。
- 刷新或连接断开不能直接被当作任务已经取消；恢复连接后重新核对真实状态。
- 自动修复可选；若采用，必须限制尝试次数并展示结果。完整的 Resolve 体验见 FR-111。
- AC-011：模拟一次模型或校验失败后，可查看原因、保留已有版本并重试；界面不会永久锁定或显示虚假的成功。

### FR-012 生成应用业务数据的边界

- 来源：BASELINE、SRC-CLOUD；关联 EXAM-003 的解释边界。
- FR-010 管理平台项目数据；生成应用保存任务、表单等业务数据是另一层能力。
- 本规格先以 FR-010 落实首版持久化，不据此断言评审只检查平台层。技术规划必须评估并说明是否让代表生成应用在同一版本预览刷新后保留业务数据。
- 如纳入，说明数据所属项目、版本和访客范围，以及修改/恢复版本时的行为；如未纳入，在支持范围和演示说明中明确。
- AC-012：技术计划明确选择业务数据持久化的范围和验收方式；不存在默认宣称支持全部后端数据能力的描述。

### FR-013 匿名用户标识与首次赠送

- 来源：用户于 2026-11-12 明确要求；本节优先于本文此前对积分的排除。
- 无需注册或登录。首次进入由服务器生成随机、稳定的用户 ID，使用 HttpOnly 会话 Cookie 识别；用户 ID 本身不作为授权凭据。
- 每个匿名用户首次获得 500 积分；重复打开、刷新、并发建立会话、服务重启不得重复发放。
- 现有匿名用户升级时也只补发一次 500 积分；已有项目与会话继续保留。历史任务缺少 usage 的，不追溯伪造用量或扣费。
- 积分显示价值为 10 积分 = 1 元，500 积分 = 50 元。此版本只提供免费赠送和消费账本，不实现充值、提现或支付。
- 保留同一浏览器的匿名会话；清除 Cookie 或换浏览器会成为另一名匿名用户。无需登录的方案不能保证现实中的每个人仅领取一次，不宣称具备实名防刷能力。
- AC-013：首次 500 积分且只有一笔赠送流水；同一会话多次打开余额和用户 ID 不变；不同用户的余额、流水和项目不能互相读取。

### FR-014 按真实 token 用量扣积分

| 项目 | 用户指定规则 |
| --- | --- |
| 输入 | 每 1,000,000 token 收取 20 积分 |
| 输出 | 每 1,000,000 token 收取 80 积分 |
| 公式 | 输入 token × 20 / 1,000,000 + 输出 token × 80 / 1,000,000 |
| 精度 | 以百万分之一积分精确记账；禁止逐次取整为整积分或使用二进制浮点累计 |

- 以供应商返回的 prompt_tokens / completion_tokens 为准，缓存输入仍按统一输入价；思考 token 若供应商已计入 completion_tokens，不重复加计。
- 初始生成、后续修改和自动修复各自结算；已产生真实用量但产物校验失败、拒绝或截断，也按用量记账。没有发出模型请求、明确拒绝的认证/参数错误，不扣 token 积分。
- 每次模型调用只有一笔有效扣费。HTTP 幂等重放、事件重放、重复结算和页面刷新不得重复扣费。
- 请求前检查可用积分并预授权；每次修复前重新检查。余额不足不能发送付费请求，不得产生负余额。
- 网络超时、中断或 Worker 崩溃导致缺少可信 usage 时，标为“待核对”并冻结相应预授权；不得把估算值冒充真实扣费。维护者可以根据供应商账单核对结算或释放。
- AC-014：1,000,000 输入 + 1,000,000 输出消耗 100 积分；1 输入 + 1 输出消耗 0.000100 积分；重复结算不变；并发预授权不能超支；失败用量与待核对状态可追溯。

### FR-015 输出能力与余额体验

- 取消项目自行规定的 8192 token 输出上限、提示词内“8000 token”要求，以及按小时/天的生成次数、项目数和版本数商业限制。消费额度统一由用户积分控制。
- 输出空间取模型原生最大输出能力与账户可承受额度；余额足够时不得用旧的小输出上限压缩应用。供应商原生上下文/输出边界仍需遵守。
- 同步放宽原有 64/96 KiB 代码文件限制和响应缓冲、执行时限，使其与完整应用生成匹配；沙箱隔离、幂等、有限修复和防止资源失控的技术保护继续保留，并在技术计划明确。
- 工作台显示用户 ID、总余额、可用积分、冻结积分、累计消费、计费规则与消费明细；余额不足时给出明确反馈，已有项目、预览、历史和导出继续可用。
- 使用模型的实际能力元数据，避免省略输出参数后落回供应商默认的小上限。余额导致输出空间受限时，应有真实原因记录。
- AC-015：钱包有足够余额时，模型请求不再携带 8192 输出限制；超过旧代码尺寸的有效应用能通过；消费后余额和明细同步刷新，重启后保持。

## 10. 状态与恢复规则

### 10.1 Run 状态

| 状态 | 含义 | 合法后续状态 |
| --- | --- | --- |
| pending | 请求已建立，尚未开始实际执行 | running、failed、interrupted；若选停止功能可到 canceled |
| running | 正在生成、校验或准备交付 | succeeded、failed、interrupted；若选停止功能可进入取消流程 |
| succeeded | 实际产物完成既定校验且预览已可用 | 终态；后续请求创建新 Run |
| failed | 已确认失败，有可解释的失败阶段 | 终态；重试创建新 Run |
| interrupted | 执行被中断且无法继续，系统已确认该事实 | 终态；允许基于保留结果重新发起 |
| canceled（P1） | 已确认取消，不会再提交此 Run 的新结果 | 终态；不能只因用户点击停止就提前展示 |

连接断开是连接状态，不是 Run 终态。重连先查询真实 Run 状态；服务重启后无法恢复的活动任务应在规定时间内被识别并转为可解释的终态。

### 10.2 交付原子性

一次成功交付在用户层面应表现为：版本产物已保存、预览对应版本已就绪、Run 成功、项目当前版本一致。技术规划须提出避免部分成功造成状态冲突的方案。

如果预览就绪后运行某个交互才触发错误，保留已交付版本并把它标记为存在运行错误；不能声称基础校验保证全部业务正确。

## 12. 代表验收场景

### AT-001 从零生成可交互应用

关联：FR-001～FR-007、EXAM-001、EXAM-002、EXAM-004。

Given：新访客打开在线 Demo，生成服务可用。

When：输入“创建一个中文任务看板，可以添加任务、切换完成状态，按全部/未完成/已完成筛选”，并提交。

Then：出现真实执行反馈；完成后代码可查看，预览可添加至少两项任务、完成其中一项，并得到正确筛选结果。

### AT-002 基于现有版本修改

关联：FR-008、FR-009。

Given：AT-001 已有可用 V1。

When：请求“增加高/中/低优先级及筛选，保留添加任务、完成状态和原有筛选”。

Then：创建 V2，新增能力可操作，原有行为仍可使用；V1 代码快照保持不变。业务记录跨版本如何保留按 FR-012 的明确选择验收，不默认保证迁移。

### AT-003 平台持久化

关联：FR-002、FR-006、FR-009、FR-010。

Given：AT-002 已完成。

When：刷新平台，随后关闭标签页并从在线入口重新打开同一访客上下文。

Then：能找到项目及两次请求，当前版本仍为 V2，代码与预览对应 V2；恢复预览不必重新调用模型生成代码。

### AT-004 非法输入与重复提交

关联：FR-003、NFR-007、DATA-003。

When：提交空白/超限输入，或对有效请求快速双击提交。

Then：非法输入不产生模型任务；重复提交不产生意外重复 Run；反馈清楚且项目仍可使用。

### AT-005 不同项目隔离

关联：FR-002、FR-008、DATA-001。

When：分别生成任务看板与计算器，来回打开并修改其中一个项目。

Then：代码、消息、版本和预览分别归属正确项目；另一个项目的结果不被覆盖。

### AT-006 失败后继续

关联：FR-011、NFR-002。

Given：项目已有有效版本；通过受控测试方式制造一次模型请求失败或产物校验失败。

Then：Run 显示真实失败阶段，原有效版本可读取，重试创建独立 Run；成功重试后继续正常使用。

### AT-007 运行期间刷新与恢复

关联：FR-005、FR-010、FR-011。

When：请求执行期间刷新或断开再重连。

Then：如果执行仍在进行，恢复其真实状态并接收结果；如果已结束，读取终态；如果已确认无法恢复，说明中断并允许重新提交。不得重复生成、永久锁定或误报取消。

### AT-008 访客和预览边界

关联：NFR-003～NFR-005。

Given：两个独立访客上下文分别拥有私有项目。

Then：修改项目标识或在生成应用内尝试访问其他访客数据时，不能获得未授权信息；预览中的脚本不能读取平台密钥或控制平台工作区。

### AT-009 可选版本恢复

条件：仅在选入 FR-105 时执行。

When：从 V2 恢复 V1，再提出一次新修改。

Then：当前预览与代码恢复为 V1，V2 仍保留，新 Run 明确以恢复的 V1 为基础；业务数据不被无提示清空或回滚。

### AT-010 可选代码导出

条件：仅在选入 FR-109 时执行。

Then：导出所选版本的实际源码与必要资源，按说明可运行；需要外部服务时明确列出依赖和配置，不宣称无条件离线可用。

### AT-011 生成应用业务数据持久化

条件：仅在技术计划将 FR-012 的业务数据持久化选入时执行。

When：在代表生成应用录入数据，刷新同一版本预览或按约定重新打开。

#### FR-016 通用首页与实际交付类型

- FR-016.1：侧栏使用「首页」，首页主标题为「你想创造什么？」或同义文案。首页、游戏、幻灯片和视频入口使用居中的主创作框。网站是创作类型，入口通过首页提供。

- FR-017.1：游戏页首屏背景本身是试玩入口。待机时背景融入页面，启动后在居中创作框上方显示球、挡板和砖块。创作框保持可点击和可编辑。

## 19. 长期演进与个人代表作规格

### 19.1 演进目标与范围边界

本节将项目从短期交付原型扩展为可长期公网托管、账单可控、具备高辨识度的个人全栈 AI 系统代表作，保持单机 Docker Compose + SQLite（`DELETE` journal + 短事务）的轻量运维前提，不引入实名收银台、重型多机集群或未受控运行时外网依赖。

- GOAL-008：每次底层模型切换或提示词迭代，均可通过离线基准评测集输出首轮通过率、修复轮次、耗时与单次成本对比报告。

演进里程碑划分：
- **M1（底座与防刷，P0）**：先完成仓库模块化分层、代码质量与 CI 门禁、前端 DOM 组件单测基建（FR-032、NFR-012、NFR-013），再在此结构上交付全站每日预算熔断与体验口令（FR-025、FR-026、NFR-011）。
- **M2（展示放大器，P0）**：构建过程可回放的精选作品展厅与工作区工程透视面板（FR-027、FR-028）。
- **M3（量化基准，P1）**：离线生成质量基准评测套件与多模型回归报告（FR-029、NFR-014）。
- **M4（效率与表现力，P1）**：受控沙箱预装依赖扩展与多文件 React 增量修改协议（FR-030、FR-031、NFR-015）。

### 19.2 增量功能需求与验收条件

#### FR-025 全站每日公共预算硬熔断与优雅降级

- FR-025.1：系统支持按指定时区（默认 `Asia/Shanghai` 自然日零点重置）统计全站公共池当日消费总额（含文本调用与媒体任务），默认公共池上限为 `1000` 积分/天，公共匿名访客默认关闭高单价 Vidu 视频生成（可通过配置开启）。
- FR-025.2：当公共池当日 `已结算消费 + 活动预授权冻结` 达到上限时，新的公共匿名付费生成请求立即返回明确的预算保护错误码（`PUBLIC_DAILY_BUDGET_REACHED`）及预计重置时间说明，不创建悬空 Run，也不扣减访客余额。
- FR-025.3：触发公共预算熔断期间，全站非付费能力保持完整可用：精选作品交互预览与构建回放、打开已有项目、查看历史版本、手动编辑源码触发本地编译校验预览以及导出源码 ZIP。
- AC-025：将公共日上限设为极小值后，新匿名访客提交生成收到清晰的公共额度保护提示与口令解锁入口；浏览作品、手动编辑旧项目源码预览及导出 ZIP 全部正常，跨自然日重置后自动恢复。

#### FR-026 访客体验口令（专属通行证）

- FR-026.1：通过 SQLite 持久化表与维护 CLI 脚本（无需重启服务）管理体验口令，每枚口令支持设置标签、过期时间、总可使用积分上限、单访客绑定上限，以及是否豁免公共日熔断和是否解锁视频生成。
- FR-026.2：数据库仅保存口令的安全哈希摘要与额度流水，不在前端代码、普通响应或日志中暴露明文口令；口令校验具备失败频控保护。
- FR-026.3：钱包面板与预算熔断提示处提供「输入体验码」入口，校验通过后绑定当前会话并实时刷新可用权限与专项额度，支持按口令独立查询消费与吊销。
- AC-026：在公共日预算已熔断且默认关闭公共视频生成的环境下，输入有效体验口令后可正常发起网页与视频生成；口令超额、过期或被吊销后立即拦截并给出准确说明。

#### FR-027 构建过程可回放的精选作品展厅

- FR-027.1：内置精选案例支持附带脱敏的真实构建档案快照（`BuildStory`），记录原始提示词、主 Agent 规划摘要、总耗时、调用次数、消耗 Token/积分及关键阶段时间轴（含曾触发的校验诊断与自动修复记录）。
- FR-027.2：示例预览弹窗支持在「交互预览」「只读源码」「构建回放」之间切换；全程由本地静态数据驱动，零余额、未配置模型密钥或熔断期间均可零成本使用。
- AC-027：无痕打开首页与游戏页并点开附带构建档案的精选作品，可完整交互试玩、查看多文件源码并回放规划-校验-修复时间轴，期间无模型调用或账本变动。

#### FR-028 工作区工程透视面板（Agent & Validator Inspector）

- FR-028.1：在运行进度卡片与已保存版本详情中提供默认折叠的「工程透视」面板，展开后向技术审阅者展示底层真实执行记录（仅公开脱敏结构化字段，不含系统提示词全文或密钥）。
- FR-028.2：透视内容覆盖四部分：① `TaskPlan` 规划拆解与游戏 `mechanics` 状态/样例；② 编译器、AST 沙箱静态契约与浏览器启动/探针校验摘要；③ 历史自动修复轮次的诊断码、文件行号与修复策略；④ 关联 `model_calls` 的输入/输出 Token 与微积分明细。
- AC-028：经历自动修复并交付成功后展开工程透视面板，可见规划摘要、首轮真实失败诊断码、最终通过的浏览器校验摘要，且 Token 明细总和与钱包流水一致。

#### FR-029 离线生成质量基准评测套件（Eval Suite）

- FR-029.1：仓库提供独立的 `evals/` 目录与命令行评测工具，内置不少于 20 条版本化代表用例（涵盖持久化工具、数据快照网站、网页幻灯片、2D 棋盘/平台游戏、3D 场景及二次迭代修改）。
- FR-029.2：评测运行器驱动真实网关与独立校验容器，统计首轮编译通过率、首轮启动通过率、最终交付成功率、平均修复轮次、端到端耗时、平均积分成本及失败诊断码分布，输出结构化 JSON 与可直接发布的 Markdown 对比报告。
- AC-029：针对指定模型运行评测子集并对比两次结果文件，输出完整的分类指标与回归差异 Markdown 表格，且不污染开发环境既有数据库。

#### FR-030 多文件 React 增量修改协议

- FR-030.1：基于已有 `schema_version="2"` 多文件版本迭代修改时，支持生成 Agent 仅输出新增文件、修改后的文件全文及显式删除路径列表 `deleted_files`（禁止删除 `src/App.tsx` 与 `src/styles.css`）。
- FR-030.2：Worker 在校验前将增量变更与 `base_artifact.files` 做确定性合并（保留平台托管文件覆盖规则），合并后的完整工程执行完整编译、沙箱与浏览器验收，并以完整不可变快照保存新版本；若增量合并引发引用错误或连续同因失败，自动引导回退为全量输出。
- AC-030：对多模块 React 应用提交局部修改，模型仅输出受影响文件，平台合并未改动模块后通过验收保存新版本，未修改文件与上一版本保持一致。

#### FR-031 受控沙箱预装依赖扩展

- FR-031.1：保持预览环境零外部网络请求，扩展 `shared/runtime-dependencies.json` 与校验器打包白名单，首轮新增预装纯矢量图标库 `lucide-react`。
- FR-031.2：同步更新生成提示词白名单与源码 ZIP 导出逻辑（按实际引用写入导出工程 `package.json`），确保在线预览、沙箱静态检查与导出本地 `npm install && npm run build` 完全一致。
- AC-031：生成使用 `lucide-react` 的 React 页面可通过编译和浏览器启动验收并正常显示图标；导出 ZIP 在独立目录可构建成功。

#### FR-032 仓库模块化治理、CI 门禁与架构决策文档

- FR-032.1：保持既有 HTTP API、容器启动命令与 Alembic 迁移兼容，将 `apps/api/atoms` 下的平铺模块按职责域拆分为清晰子包（`core/`、`billing/`、`gateway/`、`domains/`、`runtime/`），消除单行高密度代码风格，确保核心域层无循环依赖。
- FR-032.2：建立 GitHub Actions CI 工作流，自动执行 `ruff check`、`ruff format --check`、TypeScript 类型检查、后端 `pytest`、Validator 单测与前端 DOM 组件单测。
- FR-032.3：升级仓库首页 `README.md` 架构导览，并在 `docs/adr/` 下沉淀至少 4 篇架构决策记录（覆盖多层沙箱与真浏览器验收、流式与中断精确计费状态机、可信代理限流与边界防护、游戏规则结构化规划）。
- AC-032：CI 全量检查通过，架构依赖单测确认核心子包零循环依赖，外部审阅者可从 `README.md` 快速定位模块分层与对应 ADR。
