# 游戏玩法拆解

先从原始需求确定主玩法、玩家输入和目标。用户明确要求及所点名游戏的核心规则写入玩法。把可选的新模式、视觉反馈和额外内容留在 enhancements。出现规则变体时以用户指定的变体为准。

在规划阶段填写 task_plan.mechanics。

- initial_state 描述开局的关键对象、位置或资源、计分与阶段。
- actions 写出关键输入或回合事件、可生效的条件和按顺序执行的 effects。说明无效输入的结果。作用相同的键盘、屏幕按钮或触控共用规则入口。
- invariants 记录稳定的边界、坐标约定、计分或更新次数。胜负、停止推进和重开恢复分别在 end_condition 与 restart 中写清。开放式玩法按实际目标填写，没有结束或重开时可用 null。
- examples 选 2 至 4 个能手动推演的例子，分别写 setup、action、expected。优先覆盖一个有效操作和一个容易出错的方向、顺序或边界。给出具体棋盘、状态值或可辨认的关卡位置。随机玩法使用固定抽样、固定种子或随机事件前的中间状态。

制作时，让规则层接收动作并得出状态与反馈，界面根据该结果更新。交付前用计划中的例子推演实际规则路径，确认输入绑定、计算顺序和界面采用的结果。生成 Agent 负责玩法自测，平台负责启动检查。修改已有项目时，以基础计划和现有规则为起点，只更新受本轮需求影响的规则或例子。旧计划未保存 mechanics 时，从现有代码与本轮需求恢复相关规则。
